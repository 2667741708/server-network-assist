WSL 能访问网络，并不能证明 Windows 应用使用的网络路径正常。浏览器可能仍在连接一个已经停止运行的本地代理，而 WSL 没有采用同样的设置。

这篇文章介绍网络助手现有的诊断入口：先比较**直连公网**与**系统应用联网**，再决定是否处理手动代理。它针对 Windows 原生应用；如果直连也失败，需要继续排查路由、出口和 DNS。

> 本文依据项目 `0.2.0-alpha` 文档和界面逻辑整理。本次改写没有新增实机联网验证。截图使用演示数据，不代表你的当前网络状态。

## 准备：确认在哪台机器操作

在出现问题的 Windows 机器上打开“服务器网络助手”桌面快捷方式。若尚未安装，先按[桌面面板安装指南](https://github.com/2667741708/server-network-assist/blob/a830b2c/docs/DESKTOP.md)完成安装。这里不需要进入 WSL，也不需要改动出口服务器。

面板中的系统代理检查针对运行面板的当前 Windows 用户。WireGuard 的连接与断开需要管理员权限；本次排查先观察状态，不必立即切换隧道。

## 第一步：刷新并比较两项探测

点击“刷新状态”，同时观察直连公网和系统应用联网：

| 直连公网 | 系统应用联网 | 下一步 |
| --- | --- | --- |
| 可用 | 可用 | 检查具体应用、目标站点及应用自己的代理设置 |
| 可用 | 不可用 | 优先检查 Windows 当前用户的手动代理或 PAC |
| 不可用 | 可用 | 当前可能依赖代理访问，先了解现有路径 |
| 不可用 | 不可用 | 继续检查本机、DNS、路由及出口网络 |

“隧道已连接”只说明连接状态，不能代替应用层验证。同样，单次公网探测成功，也不能证明所有目标网站都可访问。

## 第二步：核对手动代理的地址

打开面板的系统代理信息。若地址指向 `127.0.0.1:7897` 一类本机端口，核对对应代理软件是否在运行。这个端口只是示例，按你的实际配置判断。

[![直连可用而系统应用失败的演示界面](/projects/images/windows-proxy-diagnosis.png)](/projects/images/windows-proxy-diagnosis.png)

图中重点是两项探测结果不一致，以及手动代理的地址；主机名、地址和延迟均为演示值。点击图片可查看原图。

如果仍然需要代理，恢复对应代理服务后重新探测。不要因为看到代理地址就一律关闭它。

## 第三步：不再需要时，关闭手动代理

确认无需继续使用该手动代理后，点击“关闭手动代理”，阅读确认框再执行。程序会先备份当前代理配置，再关闭当前用户的手动代理开关。

这个动作不会删除 PAC，也不会删除代理软件自己的配置。如果软件随后重新打开系统代理，需要在该软件中调整设置。需要保留或恢复原设置时，先核对原地址及该软件的配置方式，参见[Windows 兼容说明](https://github.com/2667741708/server-network-assist/blob/a830b2c/docs/WINDOWS.md)。

## 第四步：回到真正失败的应用验证

先刷新面板，再回到原先失败的 Windows 应用，重试同一个目标。记录验证条件，避免把“探测通过”当作全部修复成功。

| 验证对象 | 应观察的结果 |
| --- | --- |
| 面板两项探测 | 直连和系统应用的状态是否改变 |
| 原先失败的应用 | 同一个网址、下载或接口请求是否恢复 |
| 代理设置 | 是否被另一个程序重新接管 |

如果原应用仍失败，保留它的错误信息，继续检查其独立设置或目标服务。若直连也失败，转入出口与路由诊断；不要反复切换代理来掩盖另一个网络层的问题。
