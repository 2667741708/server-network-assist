澜桥已经验证了一条可行路线：客户端可以通过校园私网接触源网服务器，再选择源网物理出口或源网代理出口；不在校园私网时，也可以通过公网边缘 Hub 获得长期代理服务。接下来需要解决的重点，已经从“能否连通”转为“能否稳定、可恢复、可升级地长期运行”。

本文给出一套完整优化方案。文中的主机、地址和凭据均使用抽象名称；它是一份目标架构和迁移计划，不把尚未完成的功能写成已经验收的能力。

## 一、目标与边界

澜桥要在以下网络环境中给 Windows 用户提供清晰、可控的连接路径：

- 已连接校园 Wi-Fi，但只具备校园私网通信能力；
- 已完成校园运营商认证，同时仍能访问校园私网；
- 使用校园有线网络；
- 使用手机热点、家庭宽带或普通公网；
- 本机已经运行 Clash Verge、系统代理、TUN 或其他 WireGuard；
- 可以访问一个或多个校园源网节点；
- 只能访问公网边缘 Hub；
- 网络在运行中切换、休眠、续租或短暂断线。

长期目标可以归纳为八项：

1. 自动识别当前接入环境和可达路径；
2. 将“接入通道”“公网出口”“本机流量接管”分开选择；
3. 修改网络前保存状态，失败或退出时可靠恢复；
4. 与 Clash Verge 等用户代理共存；
5. 让订阅绑定逻辑资源，而不是绑定某个长期不变的 IPv4；
6. 集中管理客户、设备、套餐、节点与出口能力；
7. 记录实际采用的路径、出口和每个阶段的耗时；
8. 形成可重复构建、灰度发布和长期维护制度。

## 二、当前基础与主要问题

现有系统已经具备 Windows 图形客户端、校园账号登录与流量查询、Wi-Fi 和以太网识别、WireGuard、Mihomo、源网物理与代理出口、公网 Hub、订阅生成、异常恢复和诊断日志等基础能力。真实使用也证明：校园账号保持登录并不妨碍客户端利用校园私网联系源网节点，公网业务仍可由源网出口承载。

但目前的工程形态仍有五类风险。

### 1. 源码和发布物缺少唯一来源

不同机器上的源码副本、候选构建、安装包和临时目录容易出现名称、版本和实际内容不一致。生产程序必须能明确追溯到一个仓库提交、一个发布标签和一份构建清单。

### 2. 客户端职责过度集中

界面、账户认证、订阅、WireGuard、Mihomo、路由、DNS、系统代理、TUN、日志和恢复集中在一个桌面进程中。一旦界面被强制关闭或更新失败，网络恢复也可能受到影响。

### 3. 连接模式由大量特例组成

源网物理出口、源网代理出口、Hub 代理、Hub WireGuard、本机 Clash、系统代理和 TUN 都已出现。如果继续用分散的条件判断叠加，连接、退出和恢复将越来越难验证。

### 4. 路由切换仍是最高风险环节

默认路由、DNS、系统代理、WireGuard 和 TUN 可能同时变化。控制服务器或隧道端点一旦被自己的新路由捕获，就会形成递归；退出后若残留路由或 DNS，用户可能彻底失去公网。

### 5. 真实网络验收仍不完整

单元测试和界面模拟无法覆盖校园 Wi-Fi、热点、Clash、网络漫游、休眠恢复和长时间运行中的全部变化。系统需要稳定、可重复的真实网络测试矩阵。

## 三、设计原则

### 控制通道先保护，业务流量后接管

启用默认路由、TUN 或系统代理前，先为订阅服务、WireGuard 外层端点、WSS 入口、源网校园私网地址和恢复接口建立明确的底层保护路径。

### 每次网络修改都是一笔事务

一次入网应遵循固定顺序：

```text
发现网络
→ 保存原始状态
→ 保护控制端点
→ 建立通道
→ 验证出口
→ 接管业务流量
→ 提交连接状态
```

任意阶段失败，都按相反顺序回滚。客户端只删除自己本次创建并登记的配置，不删除用户原有路由、代理或隧道。

### 探测失败与连接失效分开

一次 DNS、HTTP 或网卡查询超时只代表一次观测失败。客户端应使用多目标探测、连续失败阈值、恢复迟滞、指数退避和冷却期，避免因为短暂抖动退出借网。

### 订阅绑定逻辑节点

订阅授权“客户可以使用哪些节点和出口”。具体地址由控制面发布并签名。节点地址变化时，管理员更新目录即可，不应重新发放全部客户订阅。

### 普通界面不直接修改系统网络

界面负责展示状态和发送意图；Windows 系统服务执行高权限网络操作。界面退出时，连接可以按策略继续；服务异常时，恢复工具仍可独立运行。

## 四、目标架构

```text
                         ┌─────────────────────────┐
                         │ 统一控制与订阅服务      │
                         │ 客户 / 设备 / 套餐      │
                         │ 节点目录 / 策略 / 审计  │
                         └──────────┬──────────────┘
                                    │ 签名配置与状态
                 ┌──────────────────┴──────────────────┐
                 │                                     │
      ┌──────────▼──────────┐              ┌───────────▼─────────┐
      │ 公网边缘 Hub         │              │ 校园源网节点         │
      │ WSS / WireGuard     │              │ WireGuard / NAT      │
      │ 长期 Mihomo 出口     │              │ 物理出口 / 代理出口  │
      └──────────┬──────────┘              └───────────┬─────────┘
                 │                                     │
                 └──────────────────┬──────────────────┘
                                    │
                         ┌──────────▼──────────┐
                         │ Windows 系统服务    │
                         │ 路由 / DNS / 隧道   │
                         │ 心跳 / 回滚 / 日志  │
                         └───────┬─────────────┘
                                 │ 受限本地 IPC
                         ┌───────▼─────────────┐
                         │ 澜桥桌面界面         │
                         │ 订阅 / 账号 / 状态   │
                         └─────────────────────┘
```

### 控制面

控制面管理客户和设备身份、套餐与有效期、逻辑节点目录、节点健康与能力、出口授权、配置版本、撤销和审计。它不承载用户大流量数据。

### 接入与转发面

接入与转发面包括公网边缘 Hub、校园源网节点、WireGuard、HTTPS/WSS、源网物理 NAT、源网代理和 Hub 长期代理。每个节点使用统一能力描述，例如：

```json
{
  "node_id": "source-a",
  "transports": ["campus-wireguard", "public-wss"],
  "egress": ["physical", "managed-proxy"],
  "health": "ready",
  "config_revision": 12
}
```

### Windows 系统服务

系统服务负责网卡识别、路由和 DNS 快照、WireGuard 与 Mihomo 生命周期、系统代理与 TUN、保护路由、心跳、异常恢复、结构化日志和安全更新。服务只暴露受限操作，不接受界面提交任意系统命令。

### 桌面界面

界面只负责订阅、校园账号、节点与出口选择、开始和退出、恢复网络、可读诊断和脱敏诊断包。用户必须能一眼看出当前路径，而不是只看到模糊的“已入网”。

## 五、统一连接模型

把连接拆成三个正交维度：

| 维度     | 可选项                                                   |
| -------- | -------------------------------------------------------- |
| 接入通道 | 校园私网直达、源网 WireGuard、公网 WSS、Hub WireGuard    |
| 公网出口 | 源网物理出口、源网代理出口、Hub 代理出口、用户自己的代理 |
| 本机接管 | 不接管、系统代理、澜桥 TUN、与 Clash 共存                |

一个连接配置可以表示为：

```json
{
  "access": "campus-source-wireguard",
  "egress": "source-managed-proxy",
  "capture": "system-proxy",
  "fallback": ["public-hub-wss"]
}
```

推荐策略如下：

| 模式               | 前置条件            | 数据路径                    | 推荐回退     |
| ------------------ | ------------------- | --------------------------- | ------------ |
| 校园源网物理出口   | 可达校园源节点      | 客户端 → WG → 源网物理 NAT  | Hub WSS      |
| 校园源网代理出口   | 可达校园源节点      | 客户端 → WG → 源机代理      | Hub WSS      |
| Hub WSS 代理       | 可访问公网 TCP 443  | 客户端 → WSS → Hub 代理     | Hub WG       |
| Hub WireGuard 代理 | 可访问 Hub UDP 入口 | 客户端 → WG → Hub 私网代理  | Hub WSS      |
| 用户自有 Clash     | 澜桥已提供底层公网  | Clash → 澜桥路径 → 用户节点 | 澜桥系统代理 |
| 仅校园私网         | 只访问校内资源      | 校园网保持原路              | 无           |

日常公网代理优先 WSS，因为 TCP 443 的可达性通常好于任意 UDP；WireGuard保留给校园源网、Hub 私网和需要完整三层隧道的场景。本机 Clash 使用 TUN 时，澜桥不应再启动第二个全局 TUN。

## 六、事务式路由与恢复

### 建立连接

1. 获取网卡、地址、网关、DNS、路由和系统代理快照；
2. 为操作生成唯一 `connection_id`；
3. 写入网络操作所有权账本；
4. 将控制端点固定到原始物理网关；
5. 启动 WireGuard 或 Mihomo；
6. 验证握手、远端健康接口和至少一个真实出口；
7. 应用分流、系统代理或 TUN；
8. 确认控制通道未被新路由捕获；
9. 原子提交为 `CONNECTED`。

### 正常退出

1. 停止接收新的业务连接；
2. 撤销本次事务创建的系统代理或 TUN；
3. 删除本次事务登记的路由；
4. 停止本次拥有的 Mihomo 和 WireGuard；
5. 恢复原始 DNS、接口跃点和默认路由；
6. 验证基础公网或原网络；
7. 清除所有权账本。

### 崩溃恢复

系统服务启动时检查未完成事务。配置一致且通道健康时可继续接管；无法确认时执行保守回滚。独立恢复工具不得依赖主界面、订阅服务或公网。

状态机应固定为：

```text
IDLE → PREPARING → CONNECTING → VERIFYING → CONNECTED
          │             │             │           │
          └─────────────┴─────────────┘           ▼
                    ROLLING_BACK             DEGRADED
                                                 │
                                      RECONNECTING / CONNECTED
```

## 七、稳定性与心跳

稳定连接的关键不是频繁重建，而是长期保持、分层检测和有限重试。

### 分层健康检测

- 网卡层：接口、地址、网关是否有效；
- 通道层：WireGuard 最近握手、WSS 会话是否存活；
- 私网层：远端隧道地址或健康接口；
- 出口层：多个国内、校园和国际 HTTPS 目标；
- 应用层：DNS、HTTPS、代理请求能否完成。

探测至少覆盖控制服务、校园私网、国内网站和国际网站。多个目标应并发执行并设置短超时；网卡明细等慢查询移出关键路径并缓存结果。

### 重连策略

- 连续多次失败后才进入 `DEGRADED`；
- 先恢复原进程或握手，再重建当前通道；
- 当前通道确认不可用后才切换备用通道；
- 使用指数退避和随机抖动；
- 通道稳定一段时间后再清零失败计数；
- 网络漫游、休眠唤醒和地址变化走专门事件处理。

WireGuard 可配置适度保活来维持 NAT 映射，但保活不能代替真实应用层检查。

## 八、身份、订阅与节点发现

用户拿到的短字符串应是一次性或可轮换的注册令牌。注册完成后，客户端获得签名配置，不在 URL 中长期保存客户秘密。

订阅记录包含客户、设备范围、套餐、额度、有效期、允许的逻辑节点、出口类型、最大设备数、配置版本和撤销状态。客户端通过逻辑 `node_id` 获取当前校园地址、公网地址、WG/WSS 入口、能力、优先级、备用节点、过期时间和服务端签名。

首次注册时，客户端在本机生成设备密钥。服务端保存设备公钥并发放短期凭证，从而支持单设备撤销、凭证轮换、丢失设备下线和注册令牌单次使用。WireGuard 密钥必须与订阅令牌分离。

## 九、安全与权限边界

客户端侧：

- 高权限网络操作只在 Windows 服务中执行；
- IPC 使用访问控制列表；
- 凭证使用 Windows DPAPI 或系统凭据库；
- 日志不记录密码、完整令牌、私钥和代理节点凭据；
- EXE、安装包和更新包均验证签名与哈希；
- WebView 页面不获得任意系统命令能力。

服务端侧：

- 管理接口与客户数据接口分离；
- 节点只获得完成转发所需权限；
- 控制请求使用 TLS；
- 高风险操作进入审计日志；
- 登录密钥可轮换、可撤销；
- 数据库定期备份并执行恢复演练；
- 公网入口限制请求速率和异常注册行为。

网络边界：

- WireGuard 私网只开放必要服务；
- 管理端口不直接暴露公网；
- WSS 网关与内部代理通过本地或受限私网通信；
- 源网节点默认不允许客户任意访问校园内其他主机；
- 客户路由权限由订阅策略显式声明。

## 十、日志、指标和诊断包

客户端和服务端统一使用 `connection_id`、`device_id` 和脱敏后的 `subscription_id` 关联一次操作。

客户端日志需要记录：

- 当前接入网卡、接入类型和状态机变化；
- 每个连接阶段耗时；
- 路由修改前后差异；
- WireGuard 握手与 WSS/代理进程状态；
- DNS 和多目标探测摘要；
- 实际选择的节点、通道和出口；
- 重连原因、回滚步骤和结果。

服务端需要汇总在线设备、节点健康、连接数、注册与撤销事件、出口可用率、延迟、错误率、重连率、软件版本和配置版本分布。

| 指标                   | 初期目标 |
| ---------------------- | -------- |
| 可恢复连接成功率       | ≥ 99%    |
| 正常退出网络恢复成功率 | 100%     |
| 崩溃后自动恢复成功率   | ≥ 99.9%  |
| 单次探测抖动导致误退出 | 0        |
| 日志中的明文凭证       | 0        |
| 连接失败阶段可定位率   | 100%     |
| 客户端版本可追溯率     | 100%     |

诊断包默认脱敏，包含配置摘要、日志、路由差异、版本和健康结果，不包含私钥、完整令牌和账号密码。日志写入失败属于辅助功能失败，不得阻塞入网、退出或恢复。

## 十一、仓库、发布与升级治理

建立唯一权威私有仓库：`main` 只保留可发布状态，集成和功能开发在独立分支完成，正式标签不可修改。服务器安装目录和临时构建目录不能充当源码仓库。

推荐仓库布局：

```text
lanbridge/
├─ client-ui/
├─ client-service/
├─ control-plane/
├─ source-agent/
├─ edge-gateway/
├─ protocol/
├─ installer/
├─ tests/
├─ docs/
└─ deployments/
```

共享协议、状态和数据结构集中在 `protocol`。每个正式版本包含完整离线安装包、必要依赖、版本与 SHA-256 清单、数字签名、软件物料清单、升级说明、回滚包、数据库迁移说明、已知问题和验收结果。

发布通道建议划分为 `dev`、`candidate`、`stable` 和 `lts`。候选 EXE 通过真实网络矩阵之前，不覆盖稳定版。

## 十二、测试矩阵

### 网络环境

校园 Wi-Fi 未认证与已认证、校园有线、手机热点、家庭宽带、UDP 受限公网、仅校园私网、网络切换、DHCP 续租、睡眠和唤醒。

### 连接方式

源网物理出口、源网代理出口、Hub WSS、Hub WireGuard、用户 Clash、系统代理、澜桥 TUN 和仅底层网络。

### 故障注入

源网关机、Hub WSS 中断、WG 丢包、DNS 不可用、代理进程崩溃、界面崩溃、Windows 服务重启、强制关机、配置超时、订阅到期、地址变化、路由添加失败和日志目录不可写。

### 共存测试

Clash Verge 系统代理与 TUN、其他 WireGuard、Hyper-V、WSL、VPN 软件、IPv4/IPv6 和不同 Windows 防火墙配置。

### 长时间测试

按 30 分钟功能测试、5 小时稳定测试、24 小时候选验收、72 小时正式耐久测试和 7 天小范围灰度逐级推进。

## 十三、分阶段迁移计划

### 阶段 0：冻结与盘点

盘点全部源码、服务、客户端、安装包、协议和数据库；导出节点、订阅与设备清单；标记唯一生产版本；完成可恢复备份；停止从临时目录发布。

**验收：** 每个生产组件都能对应版本或构建清单，数据已备份，现有客户端可安全退出和恢复。

### 阶段 1：收拢源码与发布流程

合并有效修复，统一版本号和目录名称，自动生成离线安装包、校验文件和发布说明，补齐依赖，并建立候选与稳定版目录。

**验收：** 干净 Windows 虚拟机可离线安装，发布物可从标签重复生成，正式包可回滚。

### 阶段 2：拆分界面与系统服务

建立 Windows 服务和受限 IPC，将路由、WG、Mihomo、恢复和日志迁入服务，保留独立恢复工具，并兼容旧订阅。

**验收：** 关闭界面后连接按策略保持；服务重启后可恢复或回滚；普通用户无法执行未授权网络操作。

### 阶段 3：统一连接配置和状态机

引入接入、出口、接管三层模型，为每种模式声明前置条件、验证和回退，增加 Clash 共存策略，迁移旧配置。

**验收：** 所有模式走同一连接流程；任一步失败都进入可预期回滚；相同故障产生相同诊断码。

### 阶段 4：升级控制面与订阅

引入逻辑节点 ID、节点能力目录、短期注册令牌、设备密钥、凭证轮换、动态地址、撤销和审计。

**验收：** 节点改地址无需重发订阅；令牌不能无限重复使用；单台设备可独立撤销。

### 阶段 5：稳定性与可观测性

补齐多层健康检查、迟滞、指数退避、网络变化事件、结构化日志、指标告警和一键脱敏诊断包。

**验收：** 单目标超时不会主动退出；短暂中断可自动恢复；每次失败能定位到阶段；24 小时测试无不可恢复断网。

### 阶段 6：灰度发布与长期维护

先选择少量设备灰度，收集不同网络条件指标，分批升级，建立稳定版和长期维护版，每季度进行恢复演练并轮换密钥、清理过期设备。

**验收：** 72 小时耐久测试通过；升级和回滚都经过真实机器验证；生产告警和审计流程可用。

## 十四、里程碑与优先级

| 里程碑            | 主要成果                                   | 优先级 |
| ----------------- | ------------------------------------------ | ------ |
| M1 版本收拢       | 唯一仓库、唯一版本、可重复构建、完整离线包 | P0     |
| M2 网络服务化     | UI 与系统服务分离、独立恢复可靠            | P0     |
| M3 连接模型统一   | 三层连接配置、状态机、事务回滚             | P0     |
| M4 订阅与节点解耦 | 逻辑节点、动态地址、设备身份、撤销         | P1     |
| M5 稳定性达标     | 多目标探测、迟滞、自动重连、诊断包         | P1     |
| M6 生产发布       | 真实网络矩阵、72 小时测试、灰度升级        | P1     |

第一轮不应同时重写全部组件。最有效的顺序是先收拢版本和保证路由可逆，再拆分系统服务、统一状态机，最后升级订阅和节点目录。

## 十五、最终验收标准

长期可用版本应同时满足：

1. 新电脑无需额外下载依赖即可安装；
2. 安装包能追溯到唯一提交和标签；
3. 退出、崩溃和升级失败后均可恢复原网络；
4. 不覆盖用户原有路由、代理和 WireGuard；
5. 所有支持的通道与出口均有明确状态；
6. Clash 开启和关闭都有实测共存路径；
7. 单一探测失败不会触发主动退出；
8. 订阅不依赖固定 IPv4；
9. 日志能说明实际通道、出口和流量接管方式；
10. 日志不包含明文密码、完整令牌或私钥；
11. 源网不可用时不破坏用户原有公网；
12. 24 小时与 72 小时真实网络测试通过；
13. 升级和回滚均有自动流程；
14. 管理员可以撤销设备、轮换凭证和替换节点地址；
15. 生产组件具有健康检查、备份和恢复方案。

## 十六、风险与回滚

| 风险                   | 缓解措施               | 回滚方式                       |
| ---------------------- | ---------------------- | ------------------------------ |
| 新系统服务影响现有连接 | 候选通道与小范围灰度   | 恢复旧客户端并运行独立恢复工具 |
| 订阅升级不兼容         | 双版本解析和迁移期     | 控制面继续提供旧协议           |
| 节点目录错误           | 签名、版本号、缓存上版 | 回退最近有效目录               |
| WG 与 Clash TUN 冲突   | 保护路由与模式互斥     | 停止澜桥 TUN，保留底层通道     |
| 自动回退振荡           | 阈值、迟滞和冷却期     | 锁定用户选择的稳定通道         |
| 服务端升级失败         | 蓝绿部署与数据库备份   | 切回旧服务实例                 |
| 安装包依赖不全         | 干净虚拟机离线测试     | 使用上一个完整稳定包           |
| 日志泄露凭证           | 字段脱敏和自动扫描     | 轮换凭证并清理泄露日志         |

## 结语

澜桥无需推倒重做。WireGuard、Mihomo、校园源网节点、公网边缘 Hub 和订阅管理已经形成可行基础。下一阶段需要集中完成四件事：统一源码和发布版本、拆分界面与网络执行、用统一状态机管理全部路径、通过事务式路由和真实网络测试建立稳定性。

完成这些工作后，澜桥才能从一个功能丰富的实验系统，演进为可维护、可升级、可审计并适合持续部署的网络接入平台。
