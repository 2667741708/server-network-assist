# 问题与修复记录

## ERR-NET-043：明文 HTTP 入口下「复制地址」按钮永远复制不了

**现象**：用户上线后实测 —— 弹窗确实正常显示了，`.txt` 下载也正常，但点「复制地址」**内容进不了剪贴板**。

**根因**：`subscriptions.js` 的复制处理器写的是

```js
if (navigator.clipboard) navigator.clipboard.writeText(...)
else message('请手动复制已选中的地址。');
```

`navigator.clipboard` **只在安全上下文（secure context）存在** —— 即 HTTPS 或 localhost。管理面板四个入口里有三个是明文 HTTP：校园直连 `http://10.20.32.13:9182`、WireGuard `http://10.201.250.1:9180`，只有公网 `https://whm12.art` 是 HTTPS。于是在校园入口上 `navigator.clipboard` 是 `undefined`，`if` 为假，走 `else` —— **按钮从上线起就不可能复制成功**，只会提示"请手动复制"。这不是本次改动引入的，是被"弹窗看不见"这个更大的故障盖住的老问题：弹窗不显示时，用户根本走不到点复制这一步。

**线上实测证据**（Playwright 直连生产校园入口）：

```
origin = http://10.20.32.13:9182
window.isSecureContext      = false
typeof navigator.clipboard  = "undefined"
document.queryCommandSupported('copy') = true      ← 兜底可用
点击 #copy → message「请手动复制已选中的地址。」，copy 事件未触发
```

**为什么 `.txt` 下载不受影响**：它走 `URL.createObjectURL(blob)` + `<a download>`，不经过剪贴板 API，也不要求安全上下文。

**修复**：`navigator.clipboard` 可用时照旧；不可用（或写入被拒）时回落到 `<textarea>` + `document.execCommand('copy')` —— 该 API 在非安全上下文同样有效。失败时依旧把地址留为选中状态，保住手动 Ctrl+C 的退路，并且**无论如何都给出真实结果提示**。

**对照实验（同一线上页面、同一明文上下文，只替换 js）**：

| served js | 提示 | 实际复制内容 |
|---|---|---|
| 线上当前（未修复） | 请手动复制已选中的地址。 | `null`（copy 事件未触发） |
| 修复版 | 订阅地址已复制。 | ✅ 完整地址（57 字符，与输入逐字节相同） |

**回归防线**：在 `tests/subscription_admin_ui_browser.cjs` 里新增断言，运行于 `http://admin-fixture.test`（**本身就是非安全上下文**，与 9182/9180 同条件，故能真实复现）。断言先确认 `isSecureContext === false` 且 `typeof navigator.clipboard === 'undefined'`（否则这条测试什么也证明不了），再监听浏览器**真实触发的 `copy` 事件**读取剪贴板内容，比对是否为完整地址。**变异验证**：把 `copyText` 还原为修复前的无兜底逻辑，断言**变红**（`window.__copied` 为 `null`）；修复版**变绿**。

**发布与线上复验（2026-09-30 04:0x，用户授权后执行）**：按 ADR-0002 走完整发布（惰性快照 → 隔离预检 → 在线备份 → 13-z drop-in → 双向回滚演练），三入口 served js 均为修复版 `ec8a56ee…`。

复验工具是新加的 `tools/admin-copy-live-check/`（详见其 README），它**同时捕获两条路径**——包装 `navigator.clipboard.writeText` 并监听 `execCommand` 触发的 `copy` 事件——并打印**尝试序列**，因此能区分"主路径成功"和"主路径失败后兜底成功"：

| 入口 | 上下文 | 尝试序列 | 结果 |
|---|---|---|---|
| campus-9182 | 非安全 | `execCommand` | 472/472 ✅ |
| wg-9180 | 非安全 | `execCommand` | 472/472 ✅ |
| public-tls | 安全（无权限） | `clipboard.writeText → NotAllowedError → execCommand` | 472/472 ✅ |
| public-tls | 安全（已授权） | `clipboard.writeText` | 472/472 ✅，**OS 剪贴板回读一致** |

第三行是最有价值的一条：它证明**兜底链在真实页面上真的接得住**。原代码在这里没有兜底，`writeText` 被拒 = 什么都没复制；修复后同一场景仍然成功。这也说明"HTTPS 入口没问题"是错觉 —— 只要浏览器拒绝剪贴板权限（无头、权限策略、用户拒绝），老代码在 HTTPS 下同样失效。

**教训**：① 剪贴板 API 有安全上下文限制，而本面板大多数入口是明文 HTTP —— 任何用 `navigator.clipboard` 的地方都必须有兜底，并显式处理 `isSecureContext`；② "按钮有提示"不等于"按钮在工作"，验收必须断言**副作用真的发生了**（这里用浏览器原生的 `copy` 事件），而不是断言弹了句提示；③ 一个更显眼的故障会掩盖它后面的故障 —— 修好弹窗可见性，才暴露出复制一直不工作；④ **只在 localhost/HTTPS 上做过的浏览器测试抓不到这类缺陷**，因为那正是 `navigator.clipboard` 存在的环境 —— 夹具必须跑在明文 HTTP 源上，并先断言自己确实处于非安全上下文。

见 [OPS-NET-064](handoffs/2026-09-30-订阅地址弹窗不可见与地址导出.md) §9 / §9.1。

## ERR-NET-042：客户端换版脚本停在半途——服务被停掉却没人再启动它

**现象**：本机 LanBridge 客户端 0.1.53 → 0.1.62-campus-ip-direct 的换版脚本，前面每一步都成功（源/目标双重 sha256 校验、建目录、复制 8 文件、写回滚状态、`Win32_Service.Change` 改注册项并读回校验），到「重启服务」这一步抛出：

```
Stop-Service : Service 'LanBridge Windows Service (LanBridgeService)' cannot be stopped
due to the following error: Cannot stop LanBridgeService service on computer '.'.
FullyQualifiedErrorId : CouldNotStopService  /  CategoryInfo : CloseError
```

脚本随即中断。

**根因**：`Stop-Service` 抛的是 `CategoryInfo: CloseError`。服务**确实停下来了**（事后 `sc query` 为 `STOPPED`），但 cmdlet 在服务进程退出的瞬间失去了 SCM 句柄，把这个竞态当成了失败抛出。脚本里 `$ErrorActionPreference='Stop'` 把它升级为终止性错误，于是**第 72 行之后的 `Start-Service` 从来没有执行**。

**真实危害不是那句报错，而是中断留下的半应用状态**：注册表 `PathName` 已经指向 `0.1.62-campus-ip-direct`（脚本在重启之前就改完了），而服务处于 **STOPPED** —— 本机隧道全程断开，且注册项与实际运行状态不一致，光看报错文本完全看不出这一层。

**修复**：把停止逻辑从「信 cmdlet 的异常」改为「信 SCM 的实际状态」——`Stop-Service` 包 try/catch 只降级为 `Write-Warning`，再用 `Get-CimInstance Win32_Service`（每次调用都实时查 SCM，不像 `Get-Service` 的 `ServiceController` 会缓存 `Status`）轮询确认真的到 `Stopped`，超时才失败；启动同理轮询到 `Running`。

**同时修掉一个会导致数据丢失的隐患**：原脚本在「注册已指向目标」时直接 `throw`，不可重跑。但如果只是把 throw 去掉让它继续跑，它会用**当前**注册路径（已经是新版）覆写 `upgrade-state.json`，把「怎么回到 0.1.53」这个唯一记录**抹掉**。改为：注册已在目标版本时走「重新校验 + 重启」分支，且**绝不重写回滚状态文件**。

**教训**：① 多步系统变更脚本里，一个前后矛盾的中间态比一次干净失败危险得多 —— 写操作应当要么能安全重跑（幂等），要么在失败时明确回滚；② 停止/启动这类 cmdlet 的异常**不是**关于最终状态的证据，必须回头查实际状态；③ 回滚凭据的写入必须与「确实发生了变更」绑定，否则重跑就把它毁了；④ `Get-Service` 返回的 `ServiceController` 会缓存状态，要读实时状态得用 `Get-CimInstance Win32_Service`。

见 [OPS-NET-064](handoffs/2026-09-30-订阅地址弹窗不可见与地址导出.md) §6.1。

## ERR-NET-041：订阅控制台生成地址后弹窗完全不显示（连带重放结果被丢弃）

**现象**：用户在校园直连入口生成订阅地址后，「完全看不到」生成的地址 —— 弹窗不出现，页面上没有任何地方能读到地址。用户明确要求"增加一个可看到具体地址的功能"。

**根因（缺陷一：弹窗不可见）**：`subscriptions.html` 的两个 `<dialog>`（`#address-dialog`、`#reauth-dialog`）写的是 Tabler 的 `class="modal modal-blur"`。Tabler 顶层作者样式 `.modal{display:none}` **压过浏览器对 `dialog[open]` 的 UA 样式**（作者样式源的优先级高于 UA 样式源，与选择器特异性无关）。因此 `showModal()` 确实把 `open` 属性设上了、DOM 里元素存在、`dialog.open === true`，但计算样式是 `display:none`、矩形 **0×0**，屏幕上一片空白。

本项目自己的 `subscriptions.css` 里本就有 `.address-dialog{...}` 规则（含 `width:min(640px,calc(100% - 2rem))`），但从未被应用到这两个 dialog 上 —— 是一段**死代码**；`dashboard.html` 的 dialog 一直用的是正确类名，所以只有订阅控制台中招。

**为什么只靠 `dialog.open` 断言抓不到**：这是本次最关键的教训。元素"打开了"和"看得见"是两件事，任何只检查 `open` 属性或元素存在性的测试都会全绿通过。必须同时检查**计算样式 `display !== 'none'` 且 `getBoundingClientRect()` 宽高 > 0**。

**根因（缺陷二：重放结果被丢弃）**：管理端的 `fresh()` 门禁（5 分钟有效期）过期后返回 **403**（不是 401）。前端会弹重认证对话框、重新登录拿到新 CSRF、然后**重放一次**原操作 —— 这一步是正确的。但重放拿到的返回**值被直接丢弃了**，只有 `refresh()` 在跑。后果：客户和令牌**已在服务端创建成功**，而用户看到的却是"需要重新验证身份"之类的提示，地址永远不显示。这与缺陷一叠加，让"生成后看不到地址"变成必然：要么弹窗不可见，要么结果被丢。

修复是把结果回调 `onResult` 沿 `run()` → `request()` → `pendingRetry` → `submitReauth()` 一路传下去，重放成功后调用它把地址显示出来。

**附带发现（缺陷三：窄屏水平溢出）**：本机 390px 宽度下，客户管理卡片页脚的「补发开户入口」输入框带内联 `style="width: 22rem"`（352px），在 flex 行里无法收缩，把整页 `scrollWidth` 顶到 **427px**（应 ≤ 390px）。它不属于原始投诉，但位于同一条"补发/查看地址"工作流上，且违反本项目"窄屏不得溢出、长值必须可读"的 UI 规则，故一并修复（内联宽度改为 `.reissue-field` 类 + `min-width:0` + `flex` 收缩）。

**回归防线（本次新增，且已用变异体证明其有效性）**：改写 `tests/subscription_admin_ui_browser.cjs` 为 v2 真实断言，并对**修复前的代码**做了三次变异验证 —— 三处断言全部在对应变异体上**变红**、在修复版上**变绿**：

| 变异体 | 断言结果 |
|---|---|
| 把两个 dialog 的 class 改回 `modal modal-blur` | 红：`dialog must not be display:none (Tabler .modal regression)` |
| 把 `onResult: opts.onResult` 改回 `null`（丢弃重放结果） | 红：`After re-authenticating and replaying the action: dialog should be open` |
| 把 22rem 内联宽度写回输入框并删除 `.reissue-field` | 红：`No horizontal page overflow at 390px` |

`node tests/subscription_admin_ui_browser.cjs` 现已通过。

**为什么上线时没被发现**：v2 上线（OPS-NET-063）只有**服务端** 21 项生命周期脚本（TEST-NET-068），它在隔离环境里直接打 API，**结构上不可能覆盖"弹窗是否渲染"这类纯浏览器现象**；而仓库里那份浏览器夹具 `tests/subscription_admin_ui_browser.cjs` 还是 09-18 的 **v1 时代**断言（引用了 v2 已不存在的 `#result`、`#customer-address-dialog`、各表单 `confirmation` 字段等），对 v2 HTML 必然失败 —— 也就是说 v2 的浏览器层**实际上没有任何回归覆盖**。

需要说清的是：OPS-NET-063 与 TEST-NET-068/069 的记录**并未声称浏览器夹具通过**，并如实列出了"线上真实交互登录未实测"。所以这里不是记录失实，而是**覆盖缺口**：UI 重写时夹具没有同步更新，也没人发现它已经失效。本次一并修正。

**影响**：仅影响管理面板的地址收发与查看，**不影响**已签发的线路、设备绑定、计费或客户侧连接（地址生成本身在服务端一直是成功的）。已上线期间用户如需地址，只能靠浏览器开发者工具看网络响应 —— 这正是用户投诉的场景。

**教训**：① 弹窗类 UI 的验收必须验"可见性"而不只是"打开状态"；② UI 重写必须同步更新夹具，否则"有测试"是假象；③ 服务端生命周期测试不能替代浏览器层测试，两者覆盖的现象完全不同。

见 [OPS-NET-064](handoffs/2026-09-30-订阅地址弹窗不可见与地址导出.md) / REQ-NET-063 / TEST-NET-070 / ADR-0002。

## ERR-NET-040：4 条历史订阅归档地址无法解密（旧密钥不可得）

**现象**：订阅控制台 v2 上线核对时，生产库 `subscription_addresses` 的 25 条归档中有 4 条 Fernet `InvalidToken`：

| 客户 ID | 名称 | 状态 |
|---|---|---|
| `cus_e5cb7c2077ea4871978198582b9e6a46` | LanBridge LAN test 20260917 | enabled |
| `cus_39bab970852c44808861e22bdf03fc23` | LanBridge physical 1 20260917-234550 | enabled |
| `cus_8c3c8c4288b9409f855c911b028e13b2` | LanBridge physical 2 20260917-234550 | enabled |
| `cus_59433ec2fc294f099a86a749e2cbda60` | LanBridge source_proxy 1 20260917-234550 | enabled |

**四条全部是 2026-09-17 的内部测试账号**（名称本身即测试标记），**不涉及任何真实付费客户** —— 这是本问题的实际影响面。

**证据**：失败记录集中在 2026-09-17 23:40~23:45 一个 5 分钟窗口，而前后相邻记录（23:08、23:47）均能正常解密；25 条密文长度全部为 184 字节，与 `base + '/#enroll=' + token` 的 Fernet 长度吻合，说明**写入格式一致，差异在密钥**。

**根因**：推断当时该服务以另一把 `master.key` 运行（密钥轮换或换用 data 目录试跑）。**旧密钥现已不可得，无法逆向恢复**；未在库中找到对应的密钥备份。

**影响**：仅影响管理面板"查看历史开户地址"这一便利功能，对这 4 个账号会返回友好提示（"订阅地址解密失败，请核对服务端密钥备份；不要重复开户"）。**不影响线路、设备绑定、订阅状态或计费**；销毁与延长不依赖解密，功能正常。

**影响面收窄（2026-09-30 复核）**：这 4 个 ID 在事件记录中一度只写了前 12 位前缀，按前缀回查生产库确认，**四条全部是内部测试账号** —— 名称分别为 `LanBridge LAN test 20260917`、`LanBridge physical 1/2 20260917-234550`、`LanBridge source_proxy 1 20260917-234550`，与该窗口"轮换/试跑"的推断自洽（当时正在做源网物理出口与代理出口的对比测试）。**因此本问题对真实客户的实际影响为零**，处置优先级相应下调；密钥轮换的教训不变。

**现状与处置**：不修复（缺密钥），已如实记录。需要恢复可见性时对相应客户执行**补发**（`reissue`），会用当前密钥重新归档。

**教训**：密钥轮换必须以"存量归档可读"为前置条件 —— 轮换前应先用新密钥重写全部存量记录，或保留旧密钥用于解密。见 [OPS-NET-063](handoffs/2026-09-30-订阅管理控制台v2上线.md) / REQ-NET-059 / ADR-0003。

### 现象和真实证据

用户本机 WLAN 为 `10.80.62.217/19`，网关 `10.80.32.1`。d408 为 `10.20.32.14/23`，有线网关 `10.20.32.1`。本机直连 d408 的 TCP 22 和 3389 均失败，出站接口为 WLAN。

关键路由：

```text
default dev wg-d408 table 20480
0.0.0.0/1 dev na1ae90b4a36
128.0.0.0/1 dev na1ae90b4a36
default via 10.20.32.1 dev enp4s0 metric 20100
10005: from all fwmark 0xd409 lookup main
10010: from all to 10.0.0.0/8 lookup main
10020: from all lookup 20480
```

检查 `ip route get 10.80.62.217 from 10.20.32.14` 返回：

```text
10.80.62.217 from 10.20.32.14 dev na1ae90b4a36
```

有线 NetworkManager 当前持久配置为手动地址、原网关且没有额外静态路由。可推断普通状态通过直连路由和默认网关工作；尚未取得安装 VPN 前的完整历史路由快照。
