# OPS-NET-038：4090 源网代理 DNS 与透明 TLS 修复

## 故障与证据

客户订阅的 source_proxy 授权正确，出口指定 Meta。首次检查尚无租约；排查期间客户随后建立租约，10.213.40.20/32 出现近期 WireGuard 握手，服务端已计量双向流量。没有重发令牌或改变订阅。

4090 系统 DNS 将 chatgpt.com、gemini.google.com、api.openai.com 解析为不正确的地址。修复前 curl --noproxy '*' 仍经过源机 TUN：ChatGPT 证书主机名不匹配或超时，Gemini TLS EOF。同机显式 HTTP 代理 127.0.0.1:7897 可以完成证书验证，Gemini 返回 200。现有 TUN 没有域名嗅探，透明入口仅有目标 IP 时无法纠正这类错误 DNS 结果。

## 实施

4090 追加 Mihomo 域名嗅探：enable、force-dns-mapping、parse-pure-ip、override-destination；TLS 443/8443、HTTP 80/8080。私网目标跳过，原 private route-exclude-address 保留。依据[官方说明](https://wiki.metacubex.one/config/sniff/)。读取 TLS 握手域名用于目标重建，不安装中间人证书，不关闭证书验证。

scripts/repair_source_proxy_sniff.py 限定主机和 root，保存原始配置到 root-only /var/backups/sna-source-sniff-20260918/original.yaml。先执行 mihomo -t，再设置独立 systemd 4 分钟回退，再重启 mihomo.service；验收后 commit 取消待执行回退。机场订阅、节点、规则及客户权限未变；gateway-health 不重写此配置。源端代理重启可能短暂中断已有代理连接。

ChatGPT 响应包含 cf-mitigated: challenge，是浏览器验证，不能记为登录成功。API 根路径返回 OpenAI 欢迎 JSON，但状态 421，不能记为 API 调用成功。未提交用户账号、未验证模型推理。系统 DNS 污染仍存在；嗅探在透明转发层修复目标，不等于系统 DNS 已改为正确解析。ECH、QUIC、其他端口、IPv6及所有应用未验证。

修复前后 IPv4 策略路由、main 路由和 nft inet sna_relay 一致；4090 到 D321 10.20.31.134:22、5080 10.20.32.12:22、D408 10.20.32.14:22 均可达。未修改操作员电脑网络；未执行全节点双向矩阵。客户握手、双向计量证明隧道工作，不能单独证明客户浏览器访问站点成功；浏览器复测待反馈。D321 当时未连接商业隧道，不作为本次代理转发通过证据。

## 运维

只读检查源机，按网站分次执行：

```bash
sudo python3 /home/a/inspect_source_proxy_path.py --host github.com
sudo python3 /home/a/inspect_source_proxy_path.py --host gemini.google.com
sudo python3 /home/a/inspect_source_proxy_path.py --host chatgpt.com
sudo python3 /home/a/repair_source_proxy_sniff.py baseline
```

客户不用删除已添加的订阅，也不用再次兑换一次性 enr_ 令牌。重试网页；必要时退出组网，再选择原订阅开始入网。界面没有“已入网”时，检查依赖、接入、租约、握手；已入网仍失败时，记录浏览器错误和客户自己的系统代理/TUN状态，再分别检查 DNS、路径及应用层，不覆盖客户现有代理或 DNS。

订阅生成、源端进程就绪、握手、HTTPS、网站允许访问、账号登录、模型服务成功必须分别记录。关联 REQ-NET-035 / ERR-NET-025。
