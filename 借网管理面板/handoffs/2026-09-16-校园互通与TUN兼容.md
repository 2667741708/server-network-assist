# OPS-NET-TUN-001：校园互通约束及 408 客户 TUN 兼容

日期：2026-09-16。关联：[REQ-NET-002 设计约束](../设计约束.md)、[REQ-NET-001 原网络保留](../requirements_traceability.md)。

## 问题与修复

408 的原 TUN 管理器依赖已停用的 `wg-d408` 和旧开机服务，并强制绑定旧隧道。改为读取有效在线租约及当前客户 `sna...`，使用现有 Mihomo 核心、机场订阅和规则。新增独立策略表、Clash 出站标记和校园直连优先规则；客户退网先停止属于该节点的 TUN，再关闭客户 WireGuard。没有删除独立管理跳板。

第一次启动遇到 iproute2 在不存在的 FIB 表返回残缺 JSON，已按退出码及实际错误判断空表，失败时回到普通代理。退网后重开 TUN 又暴露源机 Clash 的 fake-IP DNS 引导污染，改为固定 IP 的 DoT 引导和解析，保留机场的专用解析规则。中继每十秒异步同步，刚重连时 DNS 可能过早失败；启动 TUN 前新增等待客户 WireGuard 实际握手，避免失败被 DNS 缓存。

fake-IP 排除只写入 408 的本机直连策略，不设成所有客户默认。普通无本机 Clash 客户仍可将源机 DNS 返回的 fake-IP 交回源机；408 自己的 fake-IP 由本机 TUN 接管。

## 跳板超时的区别

检查时本机经 cloud → 5080 管理 WireGuard → 408 的请求曾超时。408 与 5080 的校园 LAN 机器都在线；5080 到 408 TCP 22 返回实际 SSH banner，不能声称校园 LAN 访问失败。

已有 [OPS-NET-003 / ERR-NET-004](2026-09-16-新客户端迁移.md) 部署了管理 Endpoint 专用保护路径。再次实测 5080 的 140.143.202.144 外层入口走管理辅助 wg-fleet，5080 wg 身份探测通过。诊断期间临时将本机 d408 SSH 别名的跳板换为已验证的 5080 LAN；之后已恢复 `c201-5080-wg`，并关闭旧池后成功重新核验 d408 身份。

## 恢复与操作

在 408 执行 `sudo d408-tun off` 可回到普通代理；`sudo d408-tun stop` 停止 Clash。均不退出借网。客户面板“退出借网”关闭附属 TUN 并释放客户隧道和租约。开启 TUN 用 `sudo d408-tun enable`，验证失败自动回普通代理，并预设三分钟回退。
