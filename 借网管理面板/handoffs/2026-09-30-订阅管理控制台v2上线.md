## 1. 背景与需求

用户 2026-09-30 反馈线上订阅管理站（Tabler 之前的旧 Angular 静态页）陈旧且功能缺失：

1. 无法选择订阅地址过期时间；
2. 没有默认订阅服务入口供选择（每次手打 base URL）；
3. 登录页没有"记住我"；
4. 无销毁 / 延长 / 补发订阅地址的能力；
5. 仪表盘可用性差；
6. **每次签发新地址都必须退出登录重新输密码**；
7. 无批量签发；
8. 无法查看哪些客户端机器从哪些 IP 访问了源服务器。

用户已拍板的四项设计决策：记住登录 = 持久会话 30 天（**不存储密码**）；签发确认 = 登录后不再逐操作确认；访问日志 = 设备 API 访问日志（不解析 WG 握手、不记录完整流量）；批量签发 = 每行一个客户名的文本框 + 统一套餐/源网/有效期 + 结果表格与导出。

## 2. 部署拓扑与基线

统筹线：9182 端口由 4090 的 systemd **用户级**单元 `sna-commercial.service` 提供。

```
WorkingDirectory=/home/a/.local/share/server-network-assist-unified/releases/commercial-admin-v2-20260930
Environment=PYTHONPATH=<同上>/site
ExecStart=/usr/bin/python3 -m server_network_assist.cli serve \
          --data /home/a/.local/share/server-network-assist-commercial/data \
          --bind 0.0.0.0 --port 9182 --origin http://10.20.32.13:9182
```

发布模型：**新快照目录 + 切换 drop-in + restart**；回滚 = 切回原 drop-in。

基线权威性：线上服务端代码**领先于仓库**（含 `/client/v1/subscription-preview`、probe-lease、`client_relay_probe.py`、`client_app_routing.py` 等仓库没有的模块）。本次采取的策略是**以部署树为主干、把仓库的订阅管理侧移植上去**，而不是整体替换任一方向。

切换前的 drop-in 是 `zzzzzzzzzz-readiness-v3-20260928.conf`。注意 `sna-commercial.service.d/` 下共 **10 个** drop-in，systemd 按文件名字典序应用，**字典序最后者生效** —— 历史上每个部署版本各留一个 `zz*` 前缀文件，最后一个（10 个 z）才是实际生效配置。本次新增 `zzzzzzzzzzz-admin-v2-20260930.conf`（11 个 z）排在最后。

## 3. 实施内容

### 3.1 后端

| 模块 | 内容 |
|---|---|
| `client_access_log.py`（新） | `device_access` 表；`record()` 为 best-effort（异常吞掉，绝不阻断客户 API）；`query()` 分页过滤；`latest_per_device()`；上限 `SNA_ACCESS_LOG_MAX_ROWS`（默认 100000） |
| `subscription_archive.py` | 地址归档（Fernet 加密存储）+ 生命周期：`generate` / `view` / `reissue` / `expire` / `restore` / `generate_batch` / `statuses` |
| `app.py` | 实例化并注入访问日志与归档；新增 `GET /api/client-service/access-log`；快照新增 `base_url_presets`（`SNA_BASE_URL_PRESETS`，默认三项）；action 分发器新增 `subscription-generate-batch` / `subscription-view` / `subscription-reissue` / `subscription-address-expire` / `subscription-address-restore`；`fresh()` 文案修正为"请重新验证管理员密码（验证有效期 5 分钟）" |
| `client_service_api.py` | `access_log` 注入；在 preview、enroll 与设备认证调用处记录 |
| `client_online.py` | `parse_enrollment_url` 增加**校园私网 IP 例外**（环回/私有/链路本地字面 IP 允许 HTTP），公网仍强制 HTTPS |

**反代语义**：`remote_ip` 只取 `request.remote`，**不信任 `X-Forwarded-For`**。因此经反向代理（WG 入口 9180、公网 whm12.art）访问时，日志记录的是网关地址而非真实客户端地址。这是刻意的取舍，已在 UI 与本文档注明。

### 3.2 前端

`subscription_admin_ui/` 为源，覆盖到 `ui/`。新增/改造：登录卡片"保持登录（30 天）"；`#reauth-dialog` 单次重认证弹窗；base URL 下拉预设（`<datalist>`）；批量签发卡片（textarea + 结果表 + 复制/CSV 导出）；访问日志卡片（客户/设备/起止时间过滤 + 分页）；客户行的"补发 / 销毁未兑换地址 / 延长有效期"按钮。**删除了生成、客户订阅、出口、代理等各表单的"确认密码"字段**，并移除各操作前的重复登录确认块 —— 这是"每次签发都要重新登录"的直接原因。

`subscriptions.js` 的 `request()` 做了集中重认证：401 或 fresh() 403 → 暂存 `pendingRetry` → 弹出 `#reauth-dialog`（不堆叠）→ 用新 CSRF 重放**一次**；CSRF 失效 403 走整页刷新，不循环。

### 4.5 数据兼容性核对

生产库中的 `subscription_addresses` 表**在本次之前就已存在**，含 **25 行真实归档**（创建于 2026-09-17~09-19，非本次会话产生；现有发布目录中没有任何一个含该模块，来源应为已被清理的更早目录）。核对结论：

- 生产表 DDL 与 v2 新写的 `CREATE TABLE IF NOT EXISTS` **逐字一致** → 正确跳过，不重建、不错位；
- 外键完整：25/25 都能 JOIN 上 `customers` 与 `enrollment_tokens`；
- 密文长度全部恰好 **184 字节** = `base + '/#enroll=' + token` 的 Fernet 长度（68 字符明文 → 137 字节 → 184 base64），与 v2 写入格式一致；
- 依赖列齐备：`devices.id`、`customers.id`、`enrollment_tokens.revoked_at`、`line_grants.access_mode/proxy_config/transport_policy`。

**解密实测：25 条中 21 条可正常解密**（19 条 `http:` 前缀、2 条 `https:` 前缀），**4 条 `InvalidToken`**：

| 客户 ID | 归档时间 | 名称 |
|---|---|---|
| `cus_e5cb7c2077ea4871978198582b9e6a46` | 2026-09-17 23:40 | LanBridge LAN test 20260917 |
| `cus_39bab970852c44808861e22bdf03fc23` | 2026-09-17 23:45 | LanBridge physical 1 20260917-234550 |
| `cus_8c3c8c4288b9409f855c911b028e13b2` | 2026-09-17 23:45 | LanBridge physical 2 20260917-234550 |
| `cus_59433ec2fc294f099a86a749e2cbda60` | 2026-09-17 23:45 | LanBridge source_proxy 1 20260917-234550 |

> 表中 ID 曾一度只记录前 12 位前缀，事后按前缀回查生产库补全为完整 ID。**四条全部是内部测试账号**（名称即测试标记），非真实付费客户。

失败集中在 **23:40~23:45 一个 5 分钟窗口**内，而前后相邻记录（23:08、23:47）均正常 —— 说明那几分钟服务是用**另一把密钥**运行的（当时应为密钥轮换或换 data 目录试跑），旧密钥现已不可得。

**影响面可控**：这 4 条只影响"管理面板查看历史地址"这一便利功能，**不影响线路、设备绑定或订阅本身**。对这四条记录点"查看地址"会看到友好提示（"订阅地址解密失败，请核对服务端密钥备份；不要重复开户。"）；对它们执行**补发（reissue）会用当前密钥重新归档**，即可恢复可见性。销毁与延长不依赖解密，可正常使用。

**且四条均为内部测试账号，真实客户影响为零** —— 名称 `LanBridge LAN test / physical 1 / physical 2 / source_proxy 1 20260917` 与该 5 分钟窗口正在做的出口对比测试吻合。手验管理面板时若在这四行看到"解密失败"提示，属**已知且不涉及付费客户**的现象，不是新缺陷。

## 6. 已知限制与未验证范围

**本次未执行（不得据此宣称已修复）**：

1. **真实交互式登录验收** —— "记住我（30 天）"cookie 的 `Max-Age`、线上 CSRF 重认证弹窗流程、各按钮的真实点击，均需管理员凭据，留给用户手验。预检环境已用同一份代码验证过登录与 remember 逻辑，但**线上交互仍属未验证**。
2. **4 条 `InvalidToken` 归档** —— 需旧密钥才能恢复，当前无法解密（见 4.5）。
3. **访问日志在反代后的 IP 语义** —— 校园直连入口记录真实客户端 IP；WG 与公网入口记录的是反代网关地址。未做 `X-Forwarded-For` 解析。
4. **长会话 soak** —— 30 天会话的长期稳定性未观测。
5. **批量签发的真实生产使用** —— 仅在隔离环境验证到 3/3 与重复拒绝。

**本次未触碰**：本机（D321）网络、客户端程序、仓库中另一路 Fluent UI 前端改动（`frontend/` 及其他未提交文件）。
