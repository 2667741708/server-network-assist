# 0003. 设备访问日志与订阅地址生命周期

- **Status**: accepted
- **Date**: 2026-09-30
- **Deciders**: 项目所有者、Server Network Assist 维护者

## Context

订阅管理控制台上线时需要补齐两类管理能力，两者都涉及"记录什么"和"允许销毁什么"的判断。

**其一，用户要求看到"哪些客户端机器从哪些 IP 访问了源服务器"。** 这个需求有多种实现路径，代价与副作用差别很大：解析 WireGuard 握手、抓取流量、或在应用层记录设备 API 调用。前两者会把系统推向一个准监控产品的形态，带来隐私、存储与运维成本；后者信息量有限但边界清晰。

**其二，用户要求能够删除、销毁、延长和修改订阅地址。** 这里存在一个不可回避的冲突：订阅地址一旦被兑换（客户已经用它完成开户），它就**不再只是一条待用的凭证，而是一段已经发生的历史**。如果允许管理员"销毁"一个已兑换的地址，归档记录与客户实际状态就会脱节，且无法从地址本身恢复。

## Decision

### 1. 访问日志只记录设备认证的客户 API 请求

新增 `device_access` 表，记录**客户 / 设备 / 来源 IP / 方法 / 路径 / 时间 / User-Agent**。

明确不做的事：**不解析 WireGuard 握手，不记录完整流量，不做流量统计或内容检查**。日志回答的是"谁在什么时候从哪个地址调用了哪个接口"，不是"谁传了多少数据"。

### 2. 写入必须是 best-effort，且永不影响客户 API

`record()` 把整个插入（含裁剪）包在异常吞没中。**日志属于辅助功能，其失败绝不能阻断客户的正常充值、开户或续期请求**。这一条与项目既有的辅助日志原则一致。

### 3. 来源 IP 只取直接对端地址，不信任 `X-Forwarded-For`

记录的是 `request.remote`。理由：`X-Forwarded-For` 是**客户端可伪造**的头部，在没有可信代理白名单的情况下采信它，等于允许任何人往审计日志里写入任意 IP —— 那比不记录更有害。

代价必须如实承认：经反向代理访问时（WG 入口 9180、公网 `whm12.art`），记录到的是**代理网关的地址**，不是真实客户端。**只有校园直连入口记录真实客户端 IP。** 这一点已写入管理面板页脚与运维文档，不得被解读为"日志里的 IP 就是真实来源"。

未来若需在反代入口还原真实 IP，前提是显式配置可信代理白名单，只对白名单来源解析该头部。

### 4. 保留上限与机会式裁剪

默认上限 10 万行（`SNA_ACCESS_LOG_MAX_ROWS`），超限时删除最旧记录。裁剪是**机会式**的（在写入时按概率触发），不引入定时任务，也不阻塞写入路径。

### 5. 地址生命周期：兑换是分界线

`subscription_addresses` 表以 Fernet 加密存放开户地址（明文为 `base + '/#enroll=' + token`），四项操作各自的边界：

| 操作 | 允许条件 | 拒绝条件 |
|---|---|---|
| 查看 | 归档记录存在 | 记录不存在 → 提示补发；解密失败 → 提示核对密钥备份，**并明确劝阻重复开户** |
| 补发 `reissue` | 客户启用、有有效线路、已绑定设备数未达套餐上限 | 客户停用 / 无有效线路 / 已达设备上限（补发**不能替换**现有设备） |
| 销毁 `expire` | **仅未兑换地址** | 已兑换 → 拒绝（不能抹掉已发生的历史）；无归档记录 → 拒绝 |
| 延长 `restore` | **仅未兑换地址**，延长 24 小时，**URL 不变、不轮换** | 已兑换 → 拒绝；无归档记录 → 拒绝 |

补发会**轮换**令牌：调用既有的令牌创建逻辑，由它把先前未使用的令牌标记为已撤销（同一客户不应存在两个可用开户地址）。

销毁采用"删除归档行 + 把令牌置为已过期并标记撤销"的组合，**保留 `enrollment_tokens` 中的历史记录**（谁在何时兑换过），只抹掉"这条地址还能用"的属性。

### 6. schema 纯增量，回滚不动数据

两张表都用 `CREATE TABLE IF NOT EXISTS` 建立。对已存在的 `subscription_addresses` 表，**必须显式核对其结构与新代码的读写假设一致**（列数、列序、外键目标），不能假定 `IF NOT EXISTS` 已经处理了这个问题 —— 它不会。

本次上线前逐项核对确认：列定义逐字一致、外键 25/25 完整、密文长度与写入格式匹配。回滚发布时不触碰这两张表。

## Consequences

- Positive: 管理面板能回答"谁在何时从哪调用了什么"，满足用户的运维诉求。
- Positive: 兑换后不可销毁的规则，使归档与客户实际状态**永远一致**，杜绝了"面板说已销毁、客户其实在用"的错位。
- Positive: 补发自动轮换，避免同一客户存在多个有效开户地址。
- Positive: 不信任 XFF 消除了审计日志被客户端污染的可能。
- Negative: 反代入口下记录的 IP 是网关地址，对溯源价值有限 —— 这是**已知且已注明**的取舍。
- Positive/Negative: 10 万行上限意味着长期只保留近期活动记录，历史审计需外部归档（当前未实现）。
- Negative: 泄漏的旧地址无法追回（无旧密钥时），只能补发；本次上线即遇到 4 条此类历史记录。
- Neutral: 不做流量统计，因此不能回答"某客户用了多少流量"——那由既有的用量与租约体系负责。

## Alternatives considered

### 解析 WireGuard 握手 / 抓包统计流量

拒绝。会把系统推向监控产品形态，带来隐私、存储与运维成本，且用户明确选择的是"设备 API 访问日志"这一范围。

### 无条件信任 `X-Forwarded-For` 以还原真实客户端 IP

拒绝。该头部可被客户端伪造，会让审计日志失去可信度。正确做法是先建立可信代理白名单。

### 允许销毁已兑换的地址

拒绝。会破坏归档与客户状态的一致性，且不可恢复。需要收回客户时，应当使用**停用客户**或**补发新地址**这两个语义明确的操作。

### 延长时同时轮换 URL

拒绝。`restore` 的语义是"给这条未兑换地址多一点时间"，轮换 URL 会使其等同于补发，让用户已经发出去的地址失效。

### 用定时任务做日志裁剪

拒绝。引入额外的常驻任务与故障面；机会式裁剪足够，且完全不阻塞写入。
